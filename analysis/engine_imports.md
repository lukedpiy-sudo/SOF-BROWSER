# The module -> engine import table (`gamex86.dll` -> `SoF.exe`)

**SOLVED 2026-11-19.**  The game module does **not** import the engine's
symbols through the PE import directory.  The engine builds a **99 entry
function-pointer table** on the stack and hands it to the module's
`GetGameAPI` export, which copies it verbatim into the module's own `.data`.

This table is the module's only route into the engine, so **every** sound,
entity, file, collision and cvar call in the module goes through one of these
99 slots.  Before this was decoded the module's calls were a pile of
`call *0x5015xxxx` with no meaning.

## 1. The mechanism

| what | where |
|---|---|
| the builder | `SoF.exe 0x2005CDB0` - `sub $0x18c,%esp` and then 99 `movl $0x…,N(%esp)` writes |
| the table base | `SoF.exe 0x2005D0EF` - `lea 0x0(%esp),%eax` |
| the argument | `SoF.exe 0x2005D0FE` - `push %eax` |
| the call | `SoF.exe 0x2005D1AF` - `call 0x20065F20` (`Sys_GetGameAPI`) |
| the copy | `gamex86.dll 0x500AD9B0` - the `GetGameAPI` export |

```
gamex86.dll 0x500AD9B0:
  500ad9b6: mov    $0x63,%ecx        ; 99 dwords
  500ad9bb: mov    $0x5015c9f0,%edi
  500ad9c0: rep    movsl             ; esi -> 0x5015C9F0
```

so

> **slot i = the dword at `0x5015C9F0 + 4*i`**, and it points at the engine
> function `SoF.exe <value>`.

The table is built with `movl $0x…,N(%esp)`, where `N` is the offset from the
table base.  The `push %eax` at `0x2005D0FE` shifts `esp` by -4, so every
write *after* that point lands at `N-4` in the table - that is why slot 24 is
empty: the engine's write for it happened before the `push`, and the copy
skipped it.

`analysis/engine_imports.py` reproduces the whole thing from
`analysis/rea/sof_disasm.txt` (it tracks the stack delta and strips the
objdump byte prefix before matching the `push`):

```bash
python3 analysis/engine_imports.py
```

The **engine** column is the function in `SoF.exe`.

the module's call sites.

### 2.1 The slots the module never calls

Some slots have **no call site in the module** at all, because the engine
only offers them for the *player* DLL, which the module loads through slot
74 and which receives the engine API in a forwarded table (the module copies
the slots into its own table at `gamex86.dll 0x500B9F25` - `0x500BA060`):

| slot | why |
|---|---|
| 19, 20, 21 | the client-message writers - the engine uses them itself when it reads a client packet |
| 44, 45 | the entity-state field read and `VectorDotProduct` - unused by this build of the module |
| 57, 59 | the PVS test and the cvar check - the engine calls them from its own code |
| 62, 63, 64, 66 | the Ghoul model API - it is handed to the player DLL through the forwarded table |

The module *does* load the addresses of slots 62/63/64/66
(`gamex86.dll 0x500B9F64`, `0x500B9F71`, `0x500B9F7D`, `0x500B9F97`) and
stores them in the player API object, so those four are called from
`player.dll` at run time.

## 3. The precache wrappers

Slots 0-4 are all one-liners over the engine's asset table
(`FUN_2005d320(name, type, max, flag, actionName)`):

| slot | call | type | max | flag | the action name |
|---|---|---|---|---|---|
| 0 | `FUN_2005d530` | `0x23` | `0x100` | 1 | `"model"` (`0x20139738`) |
| 1 | `FUN_2005d550` | `0x123` | `0x164` | 1 | `"sound"` (`0x20132e2c`) |
| 2 | `FUN_2005d570` | `0x287` | `0x100` | 1 | `"effect"` (`0x20132e14`) |
| 3 | `FUN_2005d590` | `0x387` | `0x100` | 1 | `"image"` (`0x20139740`) |
| 4 | `FUN_2005d5f0` | `0x123` | `0x164` | 0 | `"remove"` (`0x20139730`) |

The action name is the 5th argument, so the engine can log which asset kind
was precached.

**A correction worth keeping:** slot 2 (`0x5015c9f8`) is the **effect**
precache, **not** the model precache.  The weapon models are precached
through it because the weapon asset *is* an effect object
(`analysis/weapon_fire.md`).  The model precache is slot 0
(`0x5015c9f0`).

## 4. The sound path

The `.os` `PlaySound` statement ends in two engine calls:

```c
/* gamex86.dll 0x5007CCB0 (FUN_5007ccb0) */
uVar5 = (*DAT_5015c9f4)(local_4, local_10, local_14, local_18, 0);
(*DAT_5015ca48)(local_8, local_c, uVar5);
```

* `DAT_5015c9f4` = **slot 1**, the engine's precache-sound: `(path, volume,
  pitch, delay, 0)` -> the sound handle;
* `DAT_5015ca48` = **slot 22**, the engine's `StartSound` wrapper, which
  forwards to **slot 23** (`SoF.exe 0x20061F50`, `StartSound` itself):

```
SoF.exe 0x2005CD30:
  2005cd56: push   %eax          ; the entity
  2005cd57: push   $0x0
  2005cd59: call   0x20061f50    ; StartSound(0, entity, channel, handle, vol, pitch, delay, 0)
```

The module pushes only three arguments for slot 22, but the four arguments it
left on the stack from the precache call (the volume, the pitch, the delay and
the 0) land exactly on the wrapper's slots 4-7 - the compiler reuses the
stack, so the wrapper really does get
`(entity, channel, handle, volume, pitch, delay, 0)`.

## 5. What this closes

* every `call *0x5015xxxx` in the module now has a name - **all 99 slots**;
* the **pmove** import (slot 81) and the **player client API** (slot 74) were
  the two the old notes were still guessing at;
* the asset precache path (slots 0-4) is the same for the models, the sounds,
  the effects and the images, so the browser's asset table can mirror it;
* the browser's `web/www/app.js` can now stub the whole table with the same
  slot numbers, which is what the engine↔browser bridge needs.

## 6. Status

**Nothing in the table is open.** All 99 slots are named and the evidence for
each name is quoted above.

Two points that are *not* RE gaps:

* the **player DLL** is present at `Soldier of Fortune/Base/player.dll`. The
  loader (`SoF.exe 0x20066100`) tries `<gamedir>/final/player.dll` first and
  then `<gamedir>/player.dll`; the latter is the shipped fallback. Its identity
  is proven by the byte-identical `Base/gamex86.dll`, and the exact
  ammo-per-shot and fire-gate fields are recovered in
  `analysis/weapon_fire.md` §13 and `analysis/rea/player_fire_constants.md`;
* slot **24** is a hole: the engine's write for it happened before the
  `push %eax` that shifts the stack, and the module never calls it.  It is
  not a "missing" import - it is simply not written.
